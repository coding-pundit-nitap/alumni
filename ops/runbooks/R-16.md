# R-16 — Automatic releases stopped

**Alerts:** `AutoDeployBlocked`, `AutoDeployOffline`, `AutoDeployBehind` (ticket).

## What it means

`alumini-deploy.timer` runs `deploy/auto-deploy.sh` after boot and every 5 minutes. It releases the newest commit on `main` once that commit's `CI OK` check succeeded and all four images exist. The live site keeps running in every case here; what stops is new releases, unless a failed rollback says otherwise.

- **Blocked:** a release failed and was rolled back, or the host cannot release on its own: the registry login, a local change in the clone, a missing setting.
- **Offline:** the host has not reached GitHub and the registry for 6 hours. It catches up without help once it can.
- **Behind:** the host can check, but the newest commit on `main` has not passed CI or its images are not published.

## Check first

All from `deploy/` on the server.

1. `journalctl -u alumini-deploy -n 50`: the script says why it stopped.
2. `./deploy.sh status`: the live release and the history. `smoke=fail` or `source=rollback` on recent lines shows a failed release.
3. `cat .auto-deploy-failed`: the commit that will not be tried again, if there is one.
4. Offline only: `git ls-remote origin refs/heads/main` and `curl -sI https://ghcr.io/v2/` from the server.
5. Behind only: the commit's `CI OK` check and **Publish images** jobs on GitHub.

## Mitigate

- **The release failed:** fix it on `main`; the next green commit releases by itself. To try the same commit again after fixing something on the server, run `rm .auto-deploy-failed`.
- **A migration was cut off** (`prisma migrate deploy` reports a failed migration): check what it did to the schema, then run `docker compose run --rm migrate pnpm --filter @nitap/database exec prisma migrate resolve --rolled-back <name>` (or `--applied <name>` if it finished), then `rm .auto-deploy-failed`. The previous release is still running.
- **A person rolled back:** `deploy.sh rollback` holds that commit back on purpose, and the alert is the reminder. Revert it on `main`, or `rm .auto-deploy-failed` to release it again.
- **The same release was cut off 3 times:** the commit is held back rather than repeating its migration. Find what stopped it (`journalctl -u alumini-deploy`, `dmesg` for the OOM killer), fix that, then `rm .auto-deploy-failed .auto-deploy-attempts`.
- **The rollback failed:** treat it as an outage (R-1). `./deploy.sh status`, then `./deploy.sh rollback <sha>` by hand. The next run retries the rollback while `.auto-deploy-inflight` exists.
- **The registry refused:** renew the login (`docker login ghcr.io`, a token with only `read:packages`), or make the four `alumini-*` packages public.
- **Local changes in the clone:** `git status`. The server runs exactly what is in git, so remove them or commit them to `main`. The next run then releases the commit by itself.
- **Offline:** restore the network. Nothing else is needed.
- **Red `main`:** fix or revert the commit. The host waits for the next green one and does not go back to an older one.

## Escalate

- The site is down after a failed rollback → R-1.
- The same commit fails on the server but passed CI, and the cause is not found → release nothing else until it is. `sudo systemctl stop alumini-deploy.timer` pauses automatic releases.

## Resolved when

`journalctl -u alumini-deploy` shows a run with no error, `./deploy.sh status` shows the newest green commit live, and `alumini_auto_deploy_blocked` is 0.
